# Media Inference Lab

Rust-first, reproducible image and video inference benchmarks, GPU profiling, and optimization evidence. Apple Silicon is the first supported development target; platform-specific collectors and runtime adapters must remain separate from the portable comparison core.

## Purpose

Measure whether a change improves a complete media-generation workload, locate the affected pipeline stages and GPU operations, and report what happened to the outputs. A faster kernel is not automatically a faster application; numerical similarity is not a visual-quality score.

The project takes inspiration from [The Grill](https://github.com/plotarmordev/thegrill)'s saved-evidence and controlled-comparison approach. This is an independent image/video project, not a fork or an LLM-serving benchmark.

## Architecture

- **Rust CLI and core:** workload definitions, runtime execution, resource guards, capture manifests, offline comparisons, and reports. Start with one Cargo package and ordinary modules, using Clap and Serde/JSON; no initial plugin framework or embedded Python.
- **MFLUX adapter:** a thin Python process in an explicitly selected environment, using the native generation API. Start with Qwen Image 2.1; record the actual imported implementation and resolved model/settings.
- **H3 adapter:** Rust launches the existing `h3.c` CLI for MiniMax-H3 and translates available native measurements. Do not rewrite the inference engine or require a chat-completions server.
- **GPU experiments:** Metal kernels and small native host programs where needed. Keep microbenchmarks separate from end-to-end claims and runtime defaults.
- **Media inspection:** existing FFmpeg/ffprobe tools with recorded versions, plus full image/video/audio decoding where required.

Share the measurement contract, not the inference implementation. Runtime progress/logs and structured results are separate; unknown or unsupported measurements stay explicit rather than becoming zeroes or estimates.

## Measurement contract

Every capture identifies its workload, hardware/OS, model revision or fingerprint, runtime/source revision, resolved generation settings, timing boundaries, cache/process policy, samples, outcomes, and artifacts. Record host end-to-end time separately from runtime phases and GPU measurements.

Use repeated baseline/candidate/unchanged-control measurements. Distinguish cold initialization from warm execution and separate throughput from latency. Keep individual samples and ordering; comparisons may be inconclusive or invalid. Failures must remain in the evidence, not disappear through automatic retries or successful-only filtering.

| Workload | Settings and output checks | Performance |
| --- | --- | --- |
| Image | Prompt, seed, resolution, steps, scheduler, guidance, batch, precision, reference inputs; actual decoding, dimensions, pixel/latent differences, visual inspection | Seconds/image and images/second at an explicitly stated batch and timing boundary |
| Video | Image-equivalent settings plus frame count, playback FPS, duration, temporal reuse, conditioning, and audio; full frame/audio decoding and temporal/output inspection | Seconds/clip and generated frames or media duration per elapsed second, never confused with playback FPS |

Fixed seeds alone do not prove determinism. Measure baseline-versus-baseline variation. Keep exact-output checks, numerical tolerances, and visual/temporal assessments separate, and disclose approximations or changed settings rather than crediting them as equivalent-work speedups.

Memory observations must state their source and scope. Process RSS, tracked tensor allocations, driver allocations, system pressure, and swap are different measurements; unavailable total GPU memory is not inferred from RSS.

## Scope and boundaries

- First complete workflow: capture real image and video runs, retain evidence, compare saved runs offline, and inspect outputs and limitations.
- Prioritize production-shape attention benchmarks, then decoder matrix work; investigate supported runtime/kernel selection before writing replacement kernels.
- Real model weights and runtimes are user-provided. No weights, credentials, private logs, or automatic artifact uploads belong in the repository.
- No new generation UI, duplicate performance website, runtime rewrite, or universal model framework. The existing performance-lab website can consume explicitly approved, sanitized reports later.
- Do not change live application deployments or workstation infrastructure as a side effect of benchmarking.

### Build and CPU verification

Use a Rust toolchain supporting edition 2024 and an existing Python 3 for metadata-fixture tests. Observed checks used Rust/Cargo 1.98.0 on Darwin arm64. The generic CPU supervisor implements macOS/Linux ownership; Linux has not been exercised. The named maintenance guardian and native collectors require Darwin and fail closed elsewhere. Default checks require no models, MLX/MFLUX installation, GPU, or model downloads.

```sh
cargo build --locked
cargo test --all-targets
cargo clippy --all-targets -- -D warnings
target/debug/mil validate examples/image-workload.json
target/debug/mil validate examples/video-workload.json
target/debug/mil validate-result \
  --workload examples/image-workload.json tests/fixtures/image-result.json
```

The examples and result fixtures are **schema-only**, not inference workloads verified against a runtime. Their artifact is a text file explicitly stating that no inference occurred. A successful CPU protocol example:

```sh
target/debug/mil supervise --cpu-only \
  --workload examples/image-workload.json \
  --root runs/cpu-example \
  --executable /bin/sh \
  --env "RESULT_FIXTURE=$PWD/tests/fixtures/image-result.json" \
  -- -eu -c '/bin/mkdir artifacts; printf "CPU schema fixture only; no inference was performed.\n" > artifacts/schema-output.txt; /bin/cp "$RESULT_FIXTURE" "$MIL_RESULT_PATH"'
```

### Versioned evidence contract

- `src/schema.rs` defines **workload version 1** and **adapter-result version 2**; `src/capture.rs` defines **capture-record version 3**, including guard provenance and transaction-bound native invocation. Unknown fields and unsupported versions are rejected. Capture-record v1/v2 evidence remains unchanged on disk but requires the corresponding earlier reader; no automatic migration occurs. Adapter-result v1 is no longer accepted: v2 makes model-level fingerprint evidence explicit instead of treating a partial file inventory as an exhaustive model fingerprint. Workload identities are unchanged by these cutovers.
- Workload identity is SHA-256 of Rust's typed JSON serialization of **all** declared fields, including prompts, reference hashes, precision/quantization, optimizations, batching, process/cache policy, video layers, reuse intervals, playback FPS, and audio. Whitespace in strings is significant; JSON formatting/key order is not. Adapters copy the supervisor-supplied identity rather than reimplement its serialization.
- Declared and resolved settings remain separate. Explicit settings cannot change. Requested `precision: "auto"` must resolve to a concrete model precision. Requested `compute_precision: null` may remain null when no override was used, or resolve to an observed concrete choice; an explicit requested compute override cannot resolve to null or another dtype. Resolved `auto` is invalid. Do not infer a compute override from model precision. Observed model/source/module/executable identity and actual cache state are separate from requests. Native adapters must reject unsupported settings; the shared schema alone does not prove runtime support.
- An available observed model requires `fingerprint`, either `{"status":"unavailable","reason":"Model fingerprint was not measured"}` or an available value containing `sha256` and its derivation `method`. A requested `model.sha256` is compared only with that available model-level observation. Independent `model.files` hashes remain partial provenance: an unrelated config hash cannot contradict an unmeasured weights fingerprint. A concrete model-level mismatch still fails validation.
- Compatibility preserves signed-zero identity in nested reference strengths, video reuse ratios, and audio-reference strengths as well as the top-level floating-point settings. A `0.0` → `-0.0` change cannot pass compatibility while changing workload identity.
- Unavailable observations carry a reason. Timings retain units, method, scope, and boundaries; RSS, tensor bytes, driver allocation, system pressure, and swap cannot substitute for each other. Host execution, cleanup, and artifact-inspection durations are separate. A null lifecycle stage duration means that stage never began; zero is a measured, millisecond-rounded duration.
- Artifact references are safe relative paths with SHA-256, byte count, and role. Traversal, reserved control-file names, symlinks, and duplicate path aliases are rejected. Duplicate and ancestor checks share Unicode canonical-normalization and lowercase keys, without changing the stored spelling. Unix capture also rejects repeated device/inode identities, including differently named hardlinks; distinct files with equal contents remain valid. Exact output evidence means artifact-hash agreement; numerical/approximate/unassessed evidence is distinct and makes no visual-quality claim.
- A run is one ordered sample (`sample_index: 0`) in a fresh process, without retries. In-process policy is representable but rejected by this supervisor. Declaring a cold/warm policy does not prove that cache state was achieved.

### Subprocess protocol and safety limits

`supervise` requires the explicit `--cpu-only` acknowledgment. It is **not** a sandbox or a GPU-idleness check. Never route inference through either CPU supervision command; the separate native path below is currently fail-closed.

The supervisor launches an explicit executable and literal argument vector in a new per-run directory. It clears the inherited environment, retains only explicit `--env KEY=VALUE` entries, and supplies:

| Variable | Meaning |
| --- | --- |
| `MIL_REQUEST_PATH` | Absolute path to the persisted workload JSON |
| `MIL_RESULT_PATH` | Absolute destination for the adapter's versioned result JSON |
| `MIL_RUN_DIR` | Absolute run directory, also the child working directory |
| `MIL_WORKLOAD_IDENTITY` | Identity of the requested workload |

Progress belongs on stdout/stderr, retained in separate logs. The adapter writes `result.json` and its relative artifacts; success requires exit zero, valid matching structured evidence, and artifact size/hash verification. This layer verifies files, **not decoded image/video/audio correctness**. Invocation argument/environment values are redacted in the manifest, but workload documents, paths, artifacts, and raw logs are private evidence and may still contain sensitive content. Nothing is automatically uploaded.

Requested/running/final manifests use atomic replacement and file/directory synchronization. Existing runs are never reused. Supply canonical real-directory roots: symlink ancestors (including macOS `/tmp` and `/var` aliases) are rejected. SIGINT/SIGTERM finalize cancellation and clean up only the owned process group. SIGKILL or power loss may leave a durable `running` record: it means unresolved owner liveness, not success or proof that the child stopped. Offline inspection never signals a process or rewrites that record.

Each requested/result JSON document and terminal manifest is bounded at 16 MiB. The initial running manifest reserves 64 KiB for terminal metadata before any child starts; retained failure text is capped at 8 KiB with an explicit truncation marker. If valid requested and result documents together exceed the terminal manifest bound, capture records `failed`, prints the run directory, and preserves actual exit/cleanup/timing evidence. Only the embedded result copy is omitted; the original `result.json`, artifacts, and logs remain intact. Ordinary filesystem errors are not reclassified as size failures.

Process ownership pins the unreaped leader until group cleanup completes. On Darwin, zombie-only groups can return `EPERM`; cleanup accepts that case only after confirming the exited owned leader is the sole listed member. Actual signal delivery and observed group quiescence are recorded separately. Trusted children must not escape with `setsid`/`setpgid`; embedding applications must not install competing child reapers. Group signaling does not prove that every descendant has exited.

Execution has an explicit deadline, bounded stdout/stderr, and polled output-size limits. Disk polling is **not a filesystem quota** and can overshoot between observations. Cleanup uses a 100 ms TERM grace and a 1 s KILL observation bound; artifact hashing has a separate 30 s cooperative deadline. Stalled filesystem I/O is not bounded by an OS-enforced timeout. Unguarded `supervise` does not perform the checks described below.

Established baseline verification at `0346b2d`: 28 CPU regression tests passed (12 schema, 16 lifecycle), with the original CLI lifecycle smoke. Review corrections were verified separately with `cargo test --test review_capture --test review_schema`: **11 new regressions passed**, and Clippy passed with warnings denied. The original suites were not rerun merely to confirm the review observations.

### CPU-only guarded supervision

`mil guard-check --config GUARD.json --output NEW-REPORT.json` acquires the project lease, collects a launch snapshot, writes a non-overwriting report, and releases the lease. Exit `0` means these observations passed, **not that a GPU window is reserved**. Contention returns `2`; a recorded denial returns `1`.

The resource-only guard config has three required fields:

| Field | Meaning |
| --- | --- |
| `min_disk_free_bytes` | Positive filesystem available-space floor; smoke used 10 GiB |
| `max_disk_growth_bytes` | Positive maximum decrease from baseline filesystem available bytes; ordinary smoke used 256 MiB |
| `sample_interval_ms` | Target observation interval, 100–1000 ms; smoke used 100 ms |

These collectors observe memory, swap and filesystem space only. They do not scan live application commands, infer queue idleness, stop services or mint lifecycle authority. Named maintenance supplies its own fresh service observations; an absent resource reading still denies execution.

For a trusted CPU fixture, use the earlier `supervise` example with `supervise-guarded --guard-config GUARD.json` instead. Keep `--cpu-only`, the same schema fixture and literal arguments. Guarded execution is capped at 600 seconds. `guards.json` records methods, config, launch baseline, subsequent observations and decisions; terminal manifests reference its SHA-256/byte count. Offline `inspect` checks that evidence and rejects completed captures containing denied observations. The report is capture-owned, excluded from adapter output accounting, separately bounded at 16 MiB, and cannot be an adapter artifact.

Fixed memory policy: launch requires at least 30% from `/usr/bin/memory_pressure -Q`; running capture cancels below 15% or when `/usr/sbin/sysctl vm.swapusage` indicates more than 512 MiB growth from baseline. These are rounded system indications, **not GPU-memory measurements**. `statvfs` supplies filesystem available bytes, not a per-run quota. Missing/malformed required observations deny execution. Each command collector has a 2-second bound and bounded output; sequential collection is not atomic and can delay polling.

The standalone guarded-supervision lease is `$HOME/.local/share/media-inference-lab/gpu.lock`. Kernel `flock` contention never triggers retries or killing another owner. Never unlink/replace the inode to “clear” a lease. Close-only release permits an owned child retaining the inherited descriptor to hold the lock after supervisor death; ownership recovers when all such descriptors close. Descendants that escape their process group or close that descriptor are outside these guarantees. The lease covers cooperating project processes only. `maintenance-cpu` instead uses an owner-private temporary `.cpu-maintenance.lock`; it never acquires the shared GPU lease.

Health, per-known-job lookup, worker absence, files/logs and the cooperating lease cannot establish global readiness. There is no manual-ready file, deserializable readiness capability or manager-reference override. Native activation requires a fresh reviewed transaction for the named scope, its exact workload/runtime identity and bounded operations, plus `mac-studio` GPU coordination. Historical reports and consumed grants cannot authorize another run. `guard-check` acquires the shared lease and writes output; it is not a read-only readiness inquiry.

### Offline PNG comparison and inspection bundles

`compare-images` reads existing files only; it does not execute an adapter or load a model. Static PNG is the supported format: unchanged 8/16-bit grayscale, grayscale-alpha, RGB or RGBA samples, including Adam7. Transparency (`tRNS`) structure is checked explicitly, not inferred from decoder ancillary events: exactly two payload bytes for grayscale or six for RGB (at either supported bit depth), at most one occurrence, before any `IDAT` and after `PLTE` if a palette is present. `tRNS` is forbidden for grayscale-alpha/RGBA. ```sh

A growing input can consume one additional oversize-sentinel byte before rejection. ### Offline full MP4 video/audio validation

`inspect-video` is an independently runnable CPU validation step for a saved H3-compatible MP4. It does not launch H3, MFLUX, a model, a GPU lease, or a maintenance transaction. Use explicitly selected existing FFmpeg/ffprobe binaries; nothing is installed or downloaded. Preserve any approved native candidate by building the current CLI into a separate target directory:

```sh
cargo build --offline --locked --bin mil \
  --target-dir /absolute/owned/cpu-validation-build
/absolute/owned/cpu-validation-build/debug/mil inspect-video \
  --workload /absolute/saved-video-workload.json \
  --video /absolute/saved-clip.mp4 \
  --ffmpeg /absolute/existing/ffmpeg \
  --ffprobe /absolute/existing/ffprobe \
  --output-dir /absolute/new-private-inspection \
  --inspection-seconds 60
```

The workload is the existing version-1 contract. This H3-compatible inspection slice requires video, batch one, **56–362 frames with `5 + 17n` spacing**, and explicit generated-audio sample rate/channels. Disabled/reference audio is rejected, not assigned invented parameters. Expected stored-raster dimensions always come from `generation.resolution`; `render_resolution` is H3's optional internal model canvas, not its output size. Requested playback FPS must be positive and at most 120. This is media-output validation, not validation that a native H3 profile supports every representable workload.

The command snapshots and hashes the source into its new private bundle, records tool paths/hashes/versions, restricts input to the local MOV/MP4 demuxer without external data references, and uses software decoding with bounded subprocess capture. It examines **every decoded video/audio frame** with FFprobe, checking exactly one video and one audio stream, frame count/dimensions/FPS/timeline, sample rate/channels, and coherent start timestamps. Separate full FFmpeg decodes hash RGB24 and little-endian float32 PCM, cross-check decoded frame/sample counts, and require audio duration within **75–125%** of video duration. No output FPS, scaling, audio-rate, or channel override repairs mismatches. Autorotation is disabled; hashes describe converted stored-raster RGB/PCM, not native tensors, encoded equality, color-managed rendering, or quality.

Bundle schema version 1 (`offline_h3_video_inspection`) retains `source.mp4`, bounded `probe.json`, per-helper diagnostics/cleanup outcomes, `first.png`, `middle.png`, `last.png`, artifact hashes, and `report.json`. The first PNG also serves as the poster. Invalid media, missing tools and unsupported requests return **1** with `valid: false` and retained evidence; input JSON/output infrastructure errors or an existing output directory return **2**. Partial files can remain on infrastructure failure; no existing bundle is overwritten. Files/directories are private (0600/0700, subject to a stricter umask).

Bounds: source and each tool binary at most 256 MiB; each image axis at most 4096 and at most four million pixels/frame; decoded RGB at most 4 GiB and PCM at most 256 MiB; frame metadata at most 4 MiB; diagnostics at most 64 KiB/helper. Full RGB/PCM streams are hashed incrementally rather than saved or buffered in memory; only the three selected RGB frames are retained for PNG publication. The 1–120 second inspection deadline is cooperative, with the existing owned CPU helper cleanup allowance afterward. These limits are not an aggregate codec-RSS bound, filesystem quota, or hard cancellation of blocked kernel calls.

`inspection_wall_seconds` covers validation and owned helper cleanup, excluding final report publication. Native model-load/text/denoise/audio-VAE/video-VAE/mux boundaries, native host time, seconds/generated clip and generation throughput remain **unavailable**. Encoded playback FPS is never reported as generation speed.

### H3 command preparation and saved-result inspection

`h3-prepare` validates and fingerprints a selected local runtime without executing it—not even `--help` or `--info`. It creates private `report.json` and, on valid preparation, `plan.json`. The plan records shell-free argv, shader working directory, cleared environment with explicit `H3_FFMPEG`/`H3_FFPROBE`, selected source/binary/shader/configuration hashes, and an absolute future MP4 path **inside the preparation directory**, never the shader/model directory.

| Profile | Output raster | Steps | Layers | Denoiser reuse | Core reuse |
| --- | --- | --- | --- | --- | --- |
| `draft` | 864×480 | 8 | 50 | 1 | 1 |
| `standard` | 1344×768 | 20 | 50 | 2 | 1 |
| `detailed` | 1344×768 | 20 | 50 | 1 | 1 |

The version-1 workload must match the profile; nothing is silently overridden. Other required settings: `scheduler: "euler"`, guidance 1, batch 1, 56–362 aligned frames, 24 playback FPS, generated 32 kHz stereo audio, fresh process and unspecified cache state. Precision is `auto` or BF16 checkpoint storage, with `compute_precision: null` and no requested weight quantization; the selected native source uses device-selected mixed BF16/FP32/int8 kernels, **not guaranteed BF16-only compute**. Negative prompts, strength and explicit cache optimizations are unsupported. The generic `examples/video-workload.json` is a schema fixture, not an H3 profile.

An explicit internal render canvas must be same-aspect multiples of 32, no larger than the output. A reduced canvas is recorded as a modified workload, not an equivalent-work baseline. First/last-frame RGB8 PNG anchors are supported with exact hashes/lengths and a recorded selected-source transformation recipe; reference paths resolve **relative to the workload file's directory**, cannot escape it, and become absolute pinned argv entries. These transformations are described, not executed or claimed as observed latent evidence. Other reference roles/combinations not represented by this interface are rejected.

```sh
"$ISOLATED_TARGET/debug/mil" h3-prepare \
  --workload /absolute/h3-draft-workload.json --profile draft \
  --binary /absolute/existing/h3 --model-dir /absolute/local/MiniMax-H3 \
  --shader-cwd /absolute/existing/shader-directory \
  --source-dir /absolute/selected/h3-source \
  --ffmpeg /absolute/existing/ffmpeg --ffprobe /absolute/existing/ffprobe \
  --output-dir /absolute/new-private-preparation

"$ISOLATED_TARGET/debug/mil" h3-inspect-result \
  --plan /absolute/new-private-preparation/plan.json \
  --stdout /absolute/saved.stdout --stderr /absolute/saved.stderr \
  --exit-code 0 --video /absolute/saved.mp4 \
  --output-dir /absolute/new-private-result-inspection --inspection-seconds 60
```

Preparation reads bounded configuration/source files and directory metadata, **never weight payloads**. Metadata inventory is not model readiness, a caller-declared revision is not verified model identity, and source hashes do not prove how the selected binary was compiled. Each metadata/source file is capped at 16 MiB, each executable at 256 MiB, and each model-component enumeration at 4096 entries. Missing inputs retain the selected paths, request and error in a failed preparation report.

`h3-inspect-result` snapshots the supplied plan and raw stdout/stderr, revalidates the plan against the still-present selected paths/hashes, and performs full video/audio inspection. Logs are capped at 8 MiB each. Parser `mil-h3-saved-profile-v1` translates only recognized profiling grammar into common timing/resource structures. Unknown, malformed, duplicate or ambiguous records leave measurements unavailable; overlapping spans are never summed, lifetime high-water allocations are not phase deltas, and GPU command timing is not total generation time.

The report explicitly sets **`execution_attested: false` and `capture_eligible: false`**. A supplied exit code is only a caller report, not an observed child outcome. Nonzero exit fails even when the MP4 validates. No trusted `AdapterResult`, `result.json`, native host duration, generation throughput or native success is manufactured. Missing/mismatched media and invalid plans retain failures. This is a complete offline inspection operation, **not a working native H3 executor or fulfillment of #15's real draft-generation criterion**. The inspection deadline is cooperative; static metadata/file operations cannot be hard-cancelled by it.

### Guardian-owned H3 codec bridge: CPU qualification

The user-approved integration keeps H3 and codecs **fork-denied**. H3's ordinary codec `posix_spawnp`/`waitpid` calls are replaced, in a separately built integration, with a small project-owned C bridge. An inherited Unix socket transports two registered tool roles and pipe descriptors; only the Rust guardian creates the actual helpers. Root and helpers are direct guardian children with separate sessions/groups, each using the existing `OwnedProcess` enrollment, membership checks and immutable settlement. An opaque bridge token is never an OS PID.

`h3-qualify-owned` exercises that bridge with **purpose-built CPU actors**, not H3, FFmpeg, model imports or simulated native results. It accepts no executable, native plan, authorization or service name. It acquires no GPU lease and performs no live-service probe/control. On Darwin, Cargo's `build.rs` compiles only the project C bridge/fixture with the existing system Clang/ar into `OUT_DIR`; no external H3 source is compiled or changed.

```sh
ISOLATED_TARGET=/absolute/new-isolated-cargo-target
CARGO_TARGET_DIR="$ISOLATED_TARGET" cargo build --locked --bin mil
"$ISOLATED_TARGET/debug/mil" h3-qualify-owned \
  --scenario success --output-dir /absolute/new-private-owned-cpu-run
```

The new directory contains `report.json`, append-only `events.jsonl`, raw stdout/stderr, and—when produced—a real 64×32 RGB PNG, raw stereo F32LE PCM and stream hashes. The C root first reads a probe pipe through EOF, then uses concurrent writers for eight RGB frames (49,152 bytes) and 10,666 stereo PCM frames (85,328 bytes). The Rust helper consumes both pipes; the guardian independently checks deterministic stream hashes and saved media. This proves descriptor transfer, EOF behavior and actual raw media delivery, **not MP4 encoding, H3 inference, audiovisual quality or model performance**.

Scenarios: `success`, `codec-failure`, `root-failure`, `cancel`, `guard-denial`, `unknown-tool`, `direct-fork`, `helper-fork`. Success returns `0`; retained failure/cancellation/denial returns `1` even when `qualification_passed` confirms the expected negative case. Setup/CLI errors return `2`. `cancel` revokes admission after the media helper starts; SIGINT/SIGTERM also request cancellation. `guard-denial` is an explicit CPU control fixture, **not an observed memory-pressure or live-GPU guard**. Actual root/helper fork attempts must fail under the unchanged sandbox; any observed successful fork remains disqualifying.

Reports retain guardian-selected commands/environment, binary/sandbox hashes, observed PID/PPID/group/session/UID/birth enrollment and original exit/settlement evidence. Enrollment is a pre-exec ownership receipt, not proof of an executed source/model. CPU reports always set `native_execution_attested`, `capture_eligible` and `restoration_authority` to `false`. Original incomplete settlement is never promoted by later natural exit, retries, polling or another reaper. This does **not** resolve the previously retained live-member `killpg` EPERM; that failure remains open.

Bounds: one outstanding helper; at most 16 helpers/32 requests; 16 KiB/request, four transferred pipe FDs and 128 arguments; targets 0–1023 excluding reserved broker FD 198. The root alone receives the broker socket. Codec output uses bounded root capture pipes; arbitrary executable/environment requests, sockets supplied as codec streams, duplicate targets, bad tokens and malformed/truncated frames fail closed. Guardian work is bounded to eight seconds, total automation to 14 seconds and each settlement to at most two seconds within that ceiling; the media helper has a three-second lifetime. Logs are capped at 64 KiB each, journal at 1 MiB, and generated media at the fixed sizes above. Kernel/filesystem calls themselves are not hard-cancellable.
